# Plan: MATE 2.0

Status: in progress. The theme of 2.0 is **workspaces**: several organisations in one
installation. Design: [workspaces.md](workspaces.md). Tracking issue: #277.

## Why a major version

- It changes who is an administrator: "admin" becomes "admin of this workspace".
- It changes what a personal access token can reach.
- It adds a required secret in production (`MATE_SECRET_KEY`).
- The migration touches a dozen tables and backfills the log tables.

All 1.x routes keep their paths, and an installation with one workspace behaves as
today. Still, an operator has to read the release notes before upgrading. That is
what the major version says.

## 1.x clients

Clients already depend on 1.x installations, and they must keep working across the
upgrade without changes. They come in through three entry points. With one
workspace, 2.0 answers each of them as 1.x does:

| Entry point | What 2.0 does | For the client |
|---|---|---|
| OpenAI API with a personal access token | The token gets the workspace of its owner's first membership: Default | No change |
| `/run_sse` through the proxy, admin credentials (Basic auth or the `/auth/token` bearer) | Platform administrator; workspace 1 when there is no `X-MATE-Workspace` | No change |
| Widget public key | The workspace comes from the key's project | No change |
| Responses that list projects, agents or logs | Gain a `workspace_id` field | No change, unless the client refuses unknown fields |

The changes that could have broken these clients already shipped in 1.5.1 and 1.6.0:

- the RBAC callback fails closed;
- the proxy runs a non-admin only on their own user id;
- Slack ids now include the team.

The risks that remain are in how an installation is upgraded, not in the API:

- **`shared/test/test_client_contract.py`** makes these calls against the real app.
  - Phases 1 and 2 are done only when it passes.
  - It does not change during them. A change to it is a breaking change and goes in
    the release notes.
- **Deploy from a release tag** (`ghcr.io/antiv/mate:1.6`), not from `main`, while 2.0
  lands. `main` will carry a migration that can't be rolled back, and a phase 2
  that is only half done.
- **Set `MATE_SECRET_KEY` on 1.6.** That way the encryption of stored secrets
  doesn't arrive together with 2.0.
- **Before 2.0.0, run on a copy of the production database:**
  - start `:main` on a separate instance, using that copy;
  - time the migration, since that is the maintenance window;
  - run the clients' main flows against it.

## What 2.0 is not

- **Isolation from a hostile tenant who can run code on the server.** Code executor
  tools, `stdio` MCP servers and hardcoded agents stay platform-admin features
  ([workspaces.md](workspaces.md#what-stays-platform-only)).
- **Self-service sign-up.** Platform administrators create workspaces.
- **Renaming agents internally.** Agent names stay unique across the installation
  ([D1](workspaces.md#d1-agent-names-stay-unique-across-the-installation)).

## 1.6: prerequisites

Each of these is worth having without workspaces, and each makes 2.0 smaller or
safer. They ship in 1.6, or in 1.5.x where they are fixes.

### Fixes found while mapping the code

All of these were checked against `main`.

1. **Widget admin file routes don't check ownership.**
   - `DELETE /widget/api/files/{file_id}` deletes any file search document by id,
     whichever project's store it is in.
   - `POST /widget/api/files/upload` accepts any `store_name`.
   - Anyone with one widget's admin key can reach another project's files.
   - Fix: only the stores of the key's project and agent.
   - **This one should go into 1.5.0** (see the 1.5.0 plan in #178).
2. **A trigger fires for any signed-in user.**
   - Without a fire key, `/triggers/{id}/fire` falls back to
     `require_dashboard_auth`, which accepts any signed-in user, not only admins.
   - The path is outside `/dashboard/api/`, so the admin middleware doesn't cover it.
   - Fix: require an admin there.
3. **The RBAC callback fails open.** It lets a model call through when the user id,
   the agent name or the agent's config is missing.
   - Make it refuse, apart from the system callers that set their own id.
   - Run the eval and trigger suites to catch the callers that relied on it.
4. **Slack users from different Slack workspaces share one MATE user.**
   - The user id is `slack_<user>`, without the team.
   - Fix: make it `slack_<team>_<user>`, keeping the old id's sessions readable.
5. **Store assignment doesn't check the project.** A file search store can be
   assigned to an agent of another project.
6. **The rate-limit middleware reads `project_id` from the request body.** It should
   take it from the agent.
7. **Deleting a project leaves rows behind:** `channel_integrations`,
   `rate_limit_config` rows for the project and its agents, and `test_cases`.

### Groundwork

8. **`project_id` on log rows.** Written on `token_usage_logs`, `guardrail_logs`,
   `agent_responses` and `audit_logs` when the row is written.
   - Usage per project then survives renames and deletes.
   - The 2.0 backfill becomes exact.
   - The workspaces design already proposed this.
9. **Encrypted secrets at rest**
   ([D7](workspaces.md#d7-secrets-at-rest)): `MATE_SECRET_KEY`, and encryption of
   `channel_integrations.bot_token`/`signing_secret` and literal
   `agents_config.model_api_key`.
   - Optional in 1.6 (a warning when unset).
   - Required in production in 2.0.
10. **`create_model()` takes the caller's context** (agent, project), even though it
    still reads the environment. It is the seam where workspace keys plug in later.
11. **One request context.** A dependency that gives each dashboard route the
    caller's identity and role, replacing the 44 `_get_is_admin` calls in
    `dashboard_server.py`.
    - It changes no behaviour in 1.6.
    - In 2.0 it carries the workspace, so the scoping work edits one function
      instead of 44 routes.
12. **The route inventory test.** The cross-workspace test lists routes from the
    router. Its skeleton, without workspaces, can land in 1.6: every
    `/dashboard/api/` route is admin-only unless allowlisted. It fails when a new
    route forgets the check.

## 2.0 phases

Each phase is one or more PRs that keep `main` releasable. All four phases ship
together as 2.0.0: without phase 3 a second workspace can only be set up from a
shell, and phase 4 is what a workspace for a client needs.

### Phase 1: schema (no behaviour change) — done (#310)

- Migration V046 on all three databases:
  - `workspaces`, with workspace 1 "Default", and `workspace_members`;
  - `workspace_id` on `projects`, `test_cases`, `rate_limit_config`, `alert_rules`
    and `personal_access_tokens` (`NOT NULL DEFAULT 1`), and on the four log tables
    (nullable);
  - the log rows are backfilled in batches at startup, from their project.
- Members are derived from `users.roles` until phase 3 edits them on their own:
  `admin` makes an owner, anyone else a member; widget visitors and pending users
  are no members.
- `workspace_id` written on new log rows, and `mate.workspace.id` on spans.
- Each table or column the design lists but nothing uses yet moved to the phase that
  first uses it:
  - `UNIQUE (team_id)` on `channel_integrations` to phase 2;
  - `workspace_invitations` and project names unique per workspace to phase 3;
  - `workspace_provider_keys` and `system_settings.workspace_id` to phase 4.
- **Done when** (all met):
  - the full suite passes on SQLite, PostgreSQL and MySQL after the migration. The
    suite runs on SQLite; V046 and the startup steps were run on PostgreSQL 16 and
    MySQL 8 over data;
  - a copy of a real 1.x database migrates in minutes, not hours. A copy of the
    production database (PostgreSQL 15.8) took 0.04 s for V046 and 0.19 s for the
    backfills;
  - `test_client_contract.py` passes, unchanged. On that copy, the OpenAI API with a
    token, the widget and `/run_sse` answered too.

### Phase 2: scoping (the security work) — done (#316–#331)

- The request context resolves the current workspace (session, token,
  `X-MATE-Workspace` for Basic auth).
- Every query is filtered by workspace:
  - dashboard routes;
  - the proxy and `/list-apps`;
  - the Work Room list;
  - the OpenAI API;
  - the MCP and A2A endpoints;
  - widget, trigger and Slack entry points;
  - the alert and rate-limit services;
  - traces and replay.
- The RBAC callback checks membership and `agent_roles`. An owner, a workspace admin
  and a platform administrator pass `allowed_for_roles` whatever their
  `agent_roles`: a user whose only role is `admin` has none.
- Users the platform creates on its own become members (role `member`) of the
  workspace of the agent or Slack integration that created them, not of Default:
  the end users an API client runs through `/run_sse`, A2A users and Slack users.
  They have no login, so the membership gives them only `agent_roles`. With one
  workspace that is what 1.x does. Widget visitors are no members.
- `UNIQUE (team_id)` on `channel_integrations`, with a pre-check that stops on
  duplicates, so a Slack lookup finds one workspace.
- Deleting a project passes its `workspace_id` to the audit log.
- `alert_service.update_rule` and `rate_limit_service.upsert_config` take an
  allowlist of fields, so `workspace_id` can't be changed through them.
- Agent create, rename and import enforce D1, and `parent_agents` stays within the
  workspace.
- The platform-only list is enforced (code-running tools, settings, wizard).
- The workspace switcher, hidden with one workspace.
- Thirteen PRs, each merged to `main` on its own. Nothing in phase 2 creates a second
  workspace, so an installation sees no change until phase 3 does.

### Phase 3: management — done (#333–#344)

- `workspace_invitations`, and project names unique per workspace instead of
  across the installation.
- Workspace settings:
  - members, roles and agent roles;
  - invitations;
  - leave and delete.
- Platform → Workspaces: create, suspend, policy flags.
  - Closing or suspending a workspace stops its agents, not only its tokens and
    dashboard: `caller_access` (proxy, A2A, `/run_live`, MCP, RBAC), widget keys,
    Slack and triggers. Nothing sets `workspaces.deleted_at` before phase 3, which
    is why the fourth review of phase 2 left it here.
- One rule for an agent with no config (a hardcoded agent), in `workspaces.py`. Today
  `_require_in_workspace` gives it to a platform administrator only, while
  `agents_outside` and `missing_from` give it to anyone in the default workspace.
  Slack's `_check_target`, the widget's `_require_target` and the test-case create
  route each restate the check. No one tells them apart before phase 3 adds default
  workspace admins without the `admin` role (seventh review of phase 2).
- Workspace-scope budgets and alerts.
- Usage and audit views per workspace, plus "All workspaces" for platform admins.
- Audit entries for every membership and settings change.
- Decisions taken for the split below:
  - **Roles leave `users.roles`** (D3). After 3e, `users.roles` holds only `admin`
    (platform administrator), `pending` and `widget`. Agent roles are edited per
    membership, the default workspace's included. The users page edits platform
    roles only. No 1.x client changes roles through the API (see
    [1.x clients](#1x-clients)), so only the release notes have to say where roles
    went.
  - **Suspend and close are two states.** `workspaces.suspended_at` is new and can
    be undone. `deleted_at` is close, allowed only for a workspace with no
    projects. Both stop the workspace the same way.
  - **Features that stay platform-only are enabled per workspace** in
    `workspaces.platform_features`, a JSON list: `code` (the code executor, stdio
    MCP servers and hardcoded agents), `server_credentials` (Google Drive, Calendar,
    Supabase Storage, the shop's `vendor_email` and `partner_key`) and `email` (a
    trigger's or alert rule's email through the server's SMTP). The default
    workspace has all three, which is what 1.x does. On save, only a platform
    administrator adds them, as in phase 2.
  - **An invitation is for one email and one workspace.** Accepting it, signed in or
    through SSO with that email, makes the user a member there and no longer
    `pending`. It does not make them a member of the default workspace.
- Ten PRs, each merged to `main` on its own. Until 3d nothing in the dashboard
  creates a second workspace, so the PRs before it change nothing a 1.x
  installation sees.
  1. **3a, one rule for an agent with no config.** One function in `workspaces.py`
     decides who reaches a hardcoded agent: a platform administrator, and in the
     default workspace only. `_require_in_workspace`, `agents_outside`,
     `missing_from`, Slack's `_check_target`, the widget's `_require_target` and the
     test-case create route call it. It has to come first, since 3e adds
     default-workspace admins without the `admin` role.
  2. **3b, schema** (V048, all three dialects). `workspace_invitations`;
     `projects` unique on `(workspace_id, name)` instead of `name`;
     `workspaces.suspended_at` and `platform_features` (`["code",
     "server_credentials", "email"]` for the default workspace, `[]` otherwise).
     - Every lookup of a project by name takes the workspace.
     - A template import whose agent names another workspace holds is refused
       (409) before it makes the project, which it would otherwise make empty. It
       doesn't prefix the workspace slug, as D1 proposed: a template sync derives
       the agent names from the project name again.
     - SQLite rebuilds `projects`; the runner turns foreign keys off around a
       SQLite migration, or `DROP TABLE` would cascade to every agent.
  3. **3c, a closed or suspended workspace stops.** One `workspace_is_open` check
     in `caller_access` (proxy, A2A, `/run_live`, MCP, the RBAC callback), widget
     keys, Slack, triggers and the alert evaluator, besides the tokens and the
     dashboard that check it already. `may_run_code()` and the other phase 2
     "default workspace only" checks read `platform_features` instead. Tested by
     setting the columns directly, before any route can.
  4. **3d, Platform → Workspaces.** A platform-only page and routes: list, create
     (name and slug), rename, suspend and resume, close, "may use platform keys"
     (stored now, used in phase 4) and `platform_features`. A new workspace gets
     its first owner from an existing user, or from an invitation once 3f lands.
     Every change is audited. The default workspace can't be suspended or closed,
     and keeps every platform feature, which the 3c guides already promise.
  5. **3e, members and roles.** Workspace settings → Members, for owners: list, change
     `role` and `agent_roles`, remove; leave the workspace. The last owner can't
     leave or be demoted. `sync_default_members()` and the `User` listeners stop
     deriving memberships from `users.roles`; they keep removing the memberships of
     a `pending` or blocked user. A workspace admin sees the members but can't
     change them. Every change is audited.
     - The first start moves each user's agent roles to their default-workspace
       membership, once (`system_settings`), and `users.roles` keeps `admin`,
       `pending` and `widget`. A user inserted with agent roles, as 1.x code writes
       them, gets them on the membership. `trigger_runner` keeps its roles.
     - `ALLOWED_API_ROLES` is matched on the agent roles of the token's workspace.
     - Going back to 1.x after this start loses the agent roles: the release notes
       say so.
  6. **3f, invitations.** An owner invites an email with a role. The link carries a
     token stored hashed, valid for 7 days, used once. It is sent by email when SMTP
     is set, else shown to copy. Accepting it, signed in or through SSO with the
     invited email, adds the membership. Listing and revoking invitations, audited.
     The OAuth allowlist (`OAUTH_ALLOWED_DOMAINS`, `OAUTH_ALLOWED_EMAILS`) still
     applies.
     - The invitation carries the role only, as V048 has it. The new member gets the
       `user` agent role, and the owner changes it on Members afterwards.
     - The response carries the link also when it was emailed, in case the mail
       doesn't arrive. The email is the platform's own, with fixed text, so it isn't
       gated by the workspace's `email` platform feature.
     - Platform → Workspaces takes `owner_email` instead of `owner`: the workspace
       starts with no member and an owner invitation.
     - The login page passes `redirect` on to single sign-on as `next`, so signing in
       from the link comes back to it.
  7. **3g, workspace budgets and alerts.** Scope `workspace` in `rate_limit_config`
     and `alert_rules`, counted over the workspace's spend and logs. The `global`

### Phase 4: provider keys per workspace

- `workspace_provider_keys`, encrypted, edited by owners.
- `system_settings.workspace_id`: a row with a workspace overrides the installation
  default, starting with the image model. Taken as a table of its own,
  `workspace_settings` (see the decisions below).
- `create_model()` uses them for the agent, fallback, image, embedding, judge and
  title models.
- "May use platform keys" per workspace, set by platform administrators.
- What the code does today (mapped on `bd9bc89`):
  - `create_model()` and the LangGraph runtime's `create_chat_model()` take a
    `ModelContext` (agent, project) and still read the environment. The agent's
    model, its fallback model, a subagent's model and the compaction summarizer
    are built through them, once, when the agent is built.
  - A `gemini-*` model goes to ADK's native `Gemini`, which builds a `google.genai`
    client from `GOOGLE_API_KEY`. ADK 2.11 takes `client_kwargs` for that client.
  - Seven other places call LiteLLM or `google.genai` directly and read the
    environment: the image tool, memory block embeddings, the eval judge, the
    improver, Work Room titles, the hallucination guardrail and the mystery game
    tools; File Search builds a `genai.Client` from `GOOGLE_API_KEY`. The wizard's
    site analyzer does too, for the platform's own wizard.
  - `${VAR}` in an agent's endpoint or MCP config is already platform-only on save
    (phase 2), and `allow_platform_keys` is stored since V046 and set on Platform →
    Workspaces since 3d, but nothing reads it.
  - `MATE_SECRET_KEY` only warns when unset; groundwork item 9 makes it required in
    production in 2.0, and no phase had taken that yet.
- Decisions taken for the split below:
  - **The key is looked up on every model call, not when the agent is built.** A
    saved, changed or deleted key, and the "may use platform keys" flag, apply to
    the next call without reloading agents. It costs one indexed read and a
    decryption per call, small beside the call itself.
  - **One order, in one function:** the agent's own key and base URL; else the
    workspace's key for the model's provider; else the environment, when the
    workspace may use platform keys; else the call fails with `This workspace has
    no key for <provider>`. It fails at call time, not when the agent is built, so
    a workspace without keys still loads its agents; it isn't a provider outage, so
    the fallback model doesn't answer it.
  - **The environment means endpoints too:** `OLLAMA_HOST`, `OPENROUTER_BASE_URL`,
    `LM_STUDIO_BASE_URL` and the like. A workspace that may not use platform keys
    reaches a local model only through its own entry with a base URL, which the
    outbound guard checks.
  - **A provider is a fixed name in code** (`google`, `openai`, `anthropic`,
    `openrouter`, `deepseek`, `mistral`, `groq`, `xai`, `ollama`), each mapped to
    the model prefixes it serves and the environment variables it replaces. `google`
    serves both the native Gemini backend and LiteLLM's `gemini/`.
  - **The default workspace always may use platform keys.** It holds what 1.x had,
    and the platform's own wizard and shop; Platform → Workspaces refuses to turn
    the flag off for it. A model built for no agent (the fallback agent, the
    wizard) uses the environment, as today. The compaction summarizer takes its
    root agent's context instead of none.
  - **`workspace_settings` instead of `system_settings.workspace_id`:** a table of
    `(workspace_id, setting_key)` beside `system_settings`, whose key is its primary
    key and would need rebuilding on three dialects, and which also holds the
    installation's own flags (3e). It starts with the image model. The judge, title
    and embedding models stay installation-wide names (`EVAL_JUDGE_MODEL`,
    `TITLE_GEN_MODEL`, `EMBEDDING_MODEL`), called with the workspace's keys. Where
    the workspace has no key for their provider, titles fall back to the first
    message and memory search to keywords, as they do on any model error; the judge
    and the improver fail with the message, and a test case can name its own judge.
  - **Keys are saved only with `MATE_SECRET_KEY` set**, in development too, and
    production refuses to start without it (unless `MATE_ALLOW_INSECURE_DEFAULTS`).
  - **Keys never leave the server once saved:** the API shows `••••1234`, the audit
    entry names the provider only, and an error or log line that would carry the
    key carries the masked form.
  - **Owners and platform administrators set keys.** A workspace admin sees which
    providers have one, masked, and can't change them, as on Members. Owners and
    admins set the workspace's image model.
- Seven PRs, each merged to `main` on its own. Until 4e no route saves a key, so the
  PRs before it change nothing a 1.x installation sees, apart from
  `MATE_SECRET_KEY` in production.
  1. **4a, schema and the secret key** (V049, all three dialects).
     `workspace_provider_keys` (`workspace_id`, `provider`, `encrypted_value`,
     `base_url`, `updated_by`, `updated_at`; unique per workspace and provider) and
     `workspace_settings`. Production refuses to start without `MATE_SECRET_KEY`.
  2. **4b, one place for credentials, and the LiteLLM models.** A
     `model_credentials(context, model_name)` in a new module returns the key and
     base URL by the order above, or raises. Both runtimes' LiteLLM clients get a
     wrapper that passes them per call, as `guard_model_client` wraps them today
     for a base URL outside the default workspace. Covers the
     agent's model, the fallback model, subagents and the compaction summarizer.
     The default workspace's flag can't be turned off. Tested with the environment
     cleared.
  3. **4c, native Gemini and File Search.** A `Gemini` built with the workspace's
     `google` key through `client_kwargs`, the client cached per key, Vertex AI off
     for it. File Search's `genai.Client` takes the store's workspace key the same
     way.
  4. **4d, the other model calls.** The image tool (and the workspace's image model
     from `workspace_settings`, also in its setup check), embeddings, the eval
     judge, the improver, Work Room titles, the hallucination guardrail and the
     mystery game tools take their workspace and call through
     `model_credentials`. The wizard's site analyzer stays on the environment.
     Tested by writing the rows directly, before any route can.
  5. **4e, Workspace settings → Models and keys.** For owners: add, replace and
     delete a provider key with an optional base URL, shown masked, and the
     workspace's image model; audited. Admins see the list. Platform → Workspaces
     shows which providers each workspace has keys for. The "Workspaces" user
     guide gets the section.
  6. **4f, an end-to-end test of the phase.** A workspace with only an OpenRouter
     key and no platform keys, set up over HTTP, runs a conversation, an eval and an
     image tool call with the environment cleared. LiteLLM's HTTP calls are caught:
     each carries the workspace's key and none an environment key. A workspace
     without a key gets the message. A key never shows in a response, an audit
     entry or a log line.
  7. **4g, what the review of the phase finds**, run as in phases 2 and 3.
- **Done when:**
  - a workspace with its own OpenRouter key and no fallback runs a conversation, an
    eval and an image tool call (4f);
  - every call is billed on its own key, checked on the provider's dashboard. This
    one is by hand, with a real key, on the instance that runs the production copy
    before 2.0.0 (see [1.x clients](#1x-clients));
  - none of these calls reads the environment, checked by a test that clears the
    environment (4b, 4f).
- For the 2.0 release notes: production refuses to start without `MATE_SECRET_KEY`
  (4a).

## Risks

| Risk | Mitigation |
|---|---|
| A route forgets the workspace filter and leaks data | One request context; the route inventory test; an independent security review per phase |
| The backfill locks a large `token_usage_logs` | Batched updates; nullable columns first; tested on a copy of a real database |
| Agent name clashes annoy users | A clear error; slug prefixes on template imports; revisit D1 if it becomes a real complaint |
| `agent_roles` moving off `users.roles` surprises existing setups | The migration copies roles per member; the release notes show where roles are now edited |
| Provider keys leak through logs or errors | Keys only in `workspace_provider_keys`, encrypted, never returned by the API after saving, redacted in errors |
| Contributors keep adding 1.x-style routes during the 2.0 work | The route inventory test fails on a route without the context; CLAUDE.md and `docs/dev/auth-and-access.md` updated first |
